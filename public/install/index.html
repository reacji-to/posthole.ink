Set up or change Posthole

A practical guide for an agent working with a person on their own computer. Use it to install Posthole, repair an existing installation, change settings, explain tradeoffs, or customize its source. Read the relevant sections before making changes. This guide describes the current repository as checked on October 24, 2026; inspect the installed version and current source when behavior differs.

Posthole is a Helium/Chrome browser extension that keeps a local archive of posts loaded while you browse X, LinkedIn, Threads, Bluesky, and Hacker News. It saves structured JSON records and, when enabled, images, videos, avatars, source data, raw responses, and fetched reply threads. A separate local viewer searches and presents the archive. The extension, native file-writing helper, archive folder, and viewer are distinct pieces; a working viewer does not prove that new posts are being captured.

Start with the person

Ask what outcome they want: a new installation, a repair, a smaller archive, a different reading style, a backup, optional publishing, or a product change. If the request already answers a question, use that answer. Avoid a lengthy interview for a straightforward local setup. Explain consequential choices in ordinary language, and make routine reversible choices without repeatedly asking for permission.

Find out the operating system, browser, browser profile, existing Posthole installation, preferred permanent source location, archive location, and whether the person wants the viewer. Ask which supported sites they actually use. Check whether they want everything captured by default or a lighter configuration with fewer media files and replies. Ask about storage constraints, computer backups, and whether they intend to keep the archive entirely local.

Treat publishing and remote sync as separate decisions. The basic installation does not require a Posthole account, a subscription, a GitHub account, or remote hosting. Do not initialize a Git repository in the archive, add a remote, push data, enable Pages, or expose the viewer to a network merely to finish local setup. If an existing archive is already a Git repository, inspect its remote and the GitHub setting before browsing: automatic sync is enabled by default.

Respect existing files, installed browser profiles, and user changes. Never replace an archive with a demo, discard uncommitted work, reset settings, regenerate the extension identity, or delete captures to get a clean result. If access to this website is password protected, obtain the site login from the user through the available secure mechanism. That website login is separate from Posthole installation and the local viewer. Do not put passwords in commands, source code, logs, or copied setup prompts.

Inspect before installing anything

Check the OS and the versions and paths of Node.js, npm, Git, and Bun when relevant. Do not assume that a tool missing from one shell is absent from the machine. Find an existing checkout or unzipped Posthole folder and inspect its README, package.json, manifest.json, Git status, and applicable AGENTS.md instructions. Record the current revision and installation path before updating it.

The native-helper installer currently targets macOS and Linux. Node.js 20 or newer is required. Bun is used for the local viewer; it is not required just to load a prebuilt extension. Git is useful for a source checkout; the GitHub CLI and Git LFS are only needed for the optional GitHub workflow. Chrome/Chromium-based browsers must allow unpacked extensions and native messaging. Managed browser policies can disable those features.

The installer detects existing Helium, Chrome, Chromium, and some Brave profile roots. On macOS it also checks Chrome Beta and Canary. That detection is implementation support, not a promise that every derivative browser or packaging method has been tested. Open the intended browser at least once to create its support directory. For Linux sandboxed packages, verify native-messaging access instead of assuming that a manifest in the usual location is sufficient. Do not present the current installer as a supported Windows installation; explain the limitation before proposing a port or a separate Linux environment.

Useful inspection commands, run without modifying the archive:

node --version
npm --version
command -v node
command -v bun
git --version

For an existing checkout, also inspect git status --short, git remote -v, and git log -1 --oneline from that checkout. Do not print authentication material that may appear in a remote URL. Locate the real browser profile rather than assuming the profile you can see is the one the user browses with.

Choose an installation route

The source repository is github.com/reacji-to/posthole. Use its README and actual implementation as the authority when this guide and a newer revision differ. The schema reference is github.com/reacji-to/posthole/blob/main/SCHEMA.md.

A source checkout is the most convenient route when the user wants updates, debugging, or customization. Choose a permanent path with them. The example below uses ~/Applications/posthole for the program and leaves ~/posthole for the archive. Do not clone over an existing directory. Replace the example path if it conflicts with the user's conventions.

mkdir -p "$HOME/Applications"
git clone https://github.com/reacji-to/posthole.git "$HOME/Applications/posthole"
cd "$HOME/Applications/posthole"
npm install
npm run build
npm run install-host

For an existing checkout, inspect its branch, remote, and uncommitted work first. Fetch and review the intended update. A fast-forward update may be appropriate for a clean tracking branch; preserve local changes and resolve divergence explicitly. Do not run a destructive reset as an update shortcut. Reinstall dependencies when their inputs change, rebuild, and rerun helper registration if the checkout or Node path changes.

The downloadable ZIP is at posthole.ink/posthole.zip. It contains a posthole folder with the prebuilt dist directory, helper, installer, source, viewer, tests, and documentation. Unzip it to a permanent location. Do not run the helper from Downloads, a temporary extraction directory, or a mounted archive that may disappear. From the unzipped posthole folder, run node scripts/install-host.mjs, then load its dist directory in the browser. Node is still required for the helper. Development dependencies are needed if you later want to rebuild or change the source; the viewer has its own dependency installation.

Keep the program directory and the archive directory separate. Moving the program after registration can break the native-helper path. Changing the archive directory does not relocate the program. Document both paths in the final handoff.

Register the native helper

The extension cannot directly write arbitrary files to a chosen folder. A small native messaging helper writes the archive. Its name is com.imbue.posthole. The installer writes a browser native-messaging manifest and generates a launcher in host/posthole-host. That launcher points to the Node executable used for installation and to this program checkout.

Run npm run install-host, or node scripts/install-host.mjs for the ZIP, using the intended Node installation. User-level registration normally does not require administrator privileges. Inspect the output: it must name at least one appropriate browser NativeMessagingHosts directory and the helper path. If it says no browser profile folder was found, launch the browser once and rerun it.

For an unusual browser location, the installer accepts a specific native-messaging manifest directory. Supply the actual directory discovered for that browser; the placeholder is not a literal path to run:

node scripts/install-host.mjs --dir /actual/browser/NativeMessagingHosts

On macOS the standard roots are under ~/Library/Application Support; on Linux they are under ~/.config. Helium's profile root is net.imput.helium. Chrome uses Google/Chrome on macOS and google-chrome on Linux. The script registers the manifest under the browser support root, not inside a guessed tab or extension folder.

The repository manifest key pins the unpacked extension ID to eeagnagddgglgkipenejhengibolcjda. The native manifest's allowed_origins must match that ID. Keep the supplied key. Never generate a new key or change allowed_origins to a wildcard to work around a broken setup. If multiple copies are installed, identify which one the user intends to keep before removing a duplicate.

If Node was moved or replaced, the launcher may still point to its old path. Rerun the installer with the desired Node binary. If the Posthole program directory was moved, rerun registration from the new location. Native messaging uses standard input/output as a protocol; do not add debugging output to the helper's standard output.

Load the browser extension

In the intended Helium profile, open helium://extensions. In Chrome, open chrome://extensions. Turn on Developer mode, choose Load unpacked, and select the Posthole program's dist folder. Do not select the archive folder, repository root, ZIP file, or viewer folder. Confirm the extension loads without a manifest error and has the expected ID.

Pin the extension in the toolbar if the user wants quick access. Open its popup and settings. Confirm the native helper is reachable before calling the installation successful. A red exclamation mark means the helper is unavailable; investigate registration, executable paths, policy, and identity rather than repeatedly reloading unrelated pages.

Posthole requests permissions to inspect supported sites, download assets, communicate with its helper, store settings, and run background work. Review the installed manifest with the user if they ask about scope. Social-site sign-in happens in the user's ordinary browser session. Ask the user to complete login themselves if needed; do not copy cookies, tokens, or credentials into scripts or the archive.

Reload a supported tab after first installation to capture the page data it loads. New builds are detected automatically through the helper, generally within about a minute; pages already open are captured from then onward. Reloading a tab also captures what it loads during that reload.

Choose the archive folder

The default archive root is ~/posthole. Set it in the extension's settings using the Save folder field or Choose button. Prefer a folder the user owns, can write to, and can back up. Inspect an existing folder before reusing it. Confirm available space, filesystem permissions, any cloud-sync behavior, and whether it is already inside a Git working tree.

For most users a dedicated directory outside a source checkout avoids accidental commits. Network disks and cloud-synced folders can add latency, conflict copies, or unavailable-file behavior. Explain those tradeoffs if relevant. A shared computer or shared folder can expose saved content to other people who have filesystem access. Ordinary JSON and media files are not an encrypted vault; use the operating system's storage and backup protections when needed.

Changing the Save folder setting directs future writes to the new root. It is not an archive migration tool. If moving existing records, pause saving, stop the viewer, back up the original, copy the entire archive including index, raw data and media, verify the copy, update settings, and restart the viewer against the new path. Keep the original until the user has checked the result. Do not merge two archives by blindly overwriting same-named files.

A lightweight setup might keep post text, images, and avatars while disabling videos and reducing reply fetching. A more complete research archive might retain media, source data, and raw responses with deeper replies. Those are choices to discuss, not hidden presets the product automatically applies. Existing captures are not deleted when future capture or download options are disabled. Do not promise that enabling an option retroactively fills every missing file or reply.

Reset counters resets the displayed session counters; it is not the way to clear, migrate, or repair an archive. Use the popup's pause control to stop new capture and its status display to see whether data is being saved. When diagnosing queued replies, also inspect the separate reply-thread setting and queue status rather than assuming every form of background work has stopped.

Understand capture and reply behavior

Posthole captures data the supported sites load during ordinary browsing, including API responses and, for some sites, embedded page data or HTML. It is not a screenshot recorder and does not guarantee a complete historical export of an account. It cannot recover posts that were never loaded, never captured, or are no longer available. Promoted posts are skipped. Reposts save the underlying original and record the repost context.

X uses GraphQL responses. Bluesky uses XRPC responses and public thread access. LinkedIn reads the feed's server-driven UI stream and supports older Voyager responses. Threads uses embedded data and subsequent GraphQL requests. Hacker News stories and item-page comments come from HTML. A site's own changes can break parsing, so a failing source may need a current build or parser fix rather than a different permission toggle.

Reply fetching is background work separate from automatic scrolling. It follows the site's API with the user's signed-in browser session where required and spaces requests per site. X also respects rate-limit information. Queues survive browser restarts. Not every discussion is public, available, or fully retrievable. Deleted, restricted, unexpanded, or rate-limited material can remain missing.

For X and LinkedIn, keep a signed-in tab of the relevant site available when thread capture needs it. Threads may need the user to open a post once so the extension can learn the request shape. If background fetching is noisy, slow, or encounters limits, lower depth/pages, turn it off, or allow the queue time to drain. Do not bypass provider limits or promise unlimited capture. The goal is a useful archive compatible with the user's normal browsing.

Optional automatic scrolling

The popup can scroll the current supported feed for a selected duration of 1–120 minutes. The user starts it intentionally. Scrolling varies in distance and pause length; it does not click posts, like anything, or turn a missing social session into a working one. It does not require the extension to switch to that tab, but the browser must remain open and the site must keep loading content.

A run stops at its deadline, when saving is paused, when the tab closes or navigates, or after a sustained period without further scrolling content. Sleep, suspended tabs, and sites pausing work in the background can interrupt it. Use Stop in the popup to end a run early. Avoid starting a long run just to test installation; a short ordinary browsing session is enough.

Save reply threads is the existing reply-fetching control, not an additional scrolling mode. Turning off auto-scroll does not necessarily empty the reply queue. Distinguish capture, scrolling, and reply fetching when the user asks to reduce activity.

Start the local viewer

The viewer is a separate Bun application. From the Posthole program directory, install its dependencies and start it:

cd viewer
bun install
bun start

Open localhost:4747. The current server binds to 127.0.0.1, so it is available on the same computer. Keep the terminal process running while the viewer is needed. Closing that process stops the viewer but does not by itself uninstall the extension or stop browser capture.

For another archive folder or an occupied port, run the server directly with explicit arguments from the viewer directory:

bun server.tsx --dir /absolute/path/to/archive --port 4748

Then open localhost:4748. Verify the chosen directory is the archive root containing index/, not a single post subfolder or the program checkout. The extension and viewer must refer to the same archive if the user expects newly captured posts to appear. The PORT environment variable is also supported; an explicit --port value takes precedence.

Do not change the loopback binding to 0.0.0.0 simply to make the viewer easier to reach. The local viewer serves captured content and media and does not inherit the public website's password protection. Network access, reverse proxies, tunnels, remote hosting, and authentication are separate work that requires the user's intended access model.

A login, background service, or auto-start-at-boot setup is not necessary for a first run. If the user wants persistence, choose a launch mechanism appropriate for their OS, record its command, working directory, logs and stop procedure, and avoid creating duplicate servers. Do not silently install a system-wide service.

Search, reading styles, and browser-local state

The current viewer offers Original style, Poster News, Postpod classic, Postpod color, Swipe, Gallery, Terminal, and Postflix. Inspect viewer/interfaces.ts for the authoritative catalog and IDs. Source filters choose where posts came from; the reading style chooses how they are displayed. Selecting a style does not change a post's origin or its saved record.

Search the saved archive, filter by source, and choose ordering in the viewer. In-order-seen and newest-first are different ordering choices. The local viewer's search should not be described as semantic/vector search merely because the optional GitHub database also contains embeddings. A style can be linked directly with a query such as ?view=ipod-color. The browser remembers the chosen interface.

Original style uses source-like cards with selectable text, saved media, and expandable content. Poster News presents expandable story rows. Gallery emphasizes media. Terminal uses a compact monospace surface. Postflix builds a featured post and horizontal media/source rows; opening a post shows its full detail view and saved video where available.

Postpod classic and color share a click-wheel layout. Previous/next moves between posts. MENU opens the post list, the wheel changes its selection, and the center button opens the selected post. The keyboard's Left opens the menu; Up/Down selects menu rows or scrolls the open post; Right opens the selected row. Space toggles the current post's video. Classic applies a two-color threshold to the display, including media; color retains full color. A post with no video cannot be made into a playable video by pressing Play.

Swipe lets the person skip left or keep right with gestures or buttons. Kept posts are local to that browser; the keep filter shows them, and the heart can remove a keep. These actions do not like or delete the original source post and do not delete archive data. Read/unread state is also stored in this browser and shared across local interfaces. Opening a story, expanding content or replies, or playing media can mark it read; simply scrolling past does not.

Browser-local preferences, keeps, and read history are distinct from the JSON archive and do not automatically transfer to a different browser or profile. Explain this before clearing site data, using private browsing, or changing profiles. Reactions belong to the separate reacji extension; do not add or imply a second Posthole reaction system.

Verify a new installation end to end

Do not end with “the commands ran.” Verify each connection. Open a supported site in the intended browser profile and browse a few ordinary posts. Check that the extension is not paused, the site is enabled, the helper reports success, and the saved-post count changes. Inspect the configured archive for a post.json and the appropriate daily index entry. If media is enabled, check that at least one saved image or video file exists rather than relying only on a remote thumbnail.

Start the viewer against that same root. Confirm that an identifiable captured post appears, its text can be searched, its source link is preserved, and its media loads. Try another interface, a long-post expansion, and a saved reply if one is available. Allow queued replies time to arrive; missing replies immediately after installation do not by themselves prove failure. If the person uses several sources, verify each relevant source independently.

Report what was actually checked and what remains unverified. Do not open a social site or log into an account the user has not authorized merely to complete a checklist. If login or browser interaction must be done by the person, give them the exact next step and keep the rest of the setup ready.

Optional GitHub sync and publishing

Only use this path when the person explicitly wants their archive sent to GitHub and understands the audience. Start by inspecting the archive's current Git status and remotes. The setup script reuses an existing repository and origin when present; a --repo argument is not permission to overwrite or retarget a different existing remote. Resolve mismatches before running it.

The workflow requires Git, a signed-in GitHub CLI, and Git LFS for large files. Check the account and repository destination without exposing tokens. New repositories default to private unless --public is passed. Repository privacy and Pages visibility are different: the supplied workflow publishes a browsable Pages archive, and the product documentation warns that it can be public even for a private repository. Confirm the current GitHub plan, Pages access behavior, quotas, and billing in the user's account rather than promising a price or a private web archive.

After approval, an example setup command from the program checkout is:

node scripts/github-setup.mjs --repo YOUR_ACCOUNT/YOUR_ARCHIVE --dir /absolute/path/to/archive

Replace both placeholders. Add --public only when the user has explicitly chosen a public repository. The script can initialize the archive repository, create or reuse its remote, push existing captured data, install the workflow, configure Pages, and start a run. It is not a harmless local preparation command. If the user wants only a backup without Pages, design and review that configuration separately instead of running this publishing setup unchanged.

With gitSync enabled, the helper attempts commits and pushes about every five minutes when the archive is a Git repository. The workflow runs about every fifteen minutes and produces a static archive plus a searchable SQLite database with embeddings. Scheduled runs can be delayed by the hosting service. Syncing a large first archive can take much longer than one interval.

The current helper routes files above roughly 95 MiB through Git LFS when available, supports its configured large-file ceiling near 2 GB per file, and splits ordinary pushes into batches around 400 MiB. A 4096 MB download cap is not a guarantee that a file can be uploaded. Inspect the helper's sync result for skipped files. Verify the current implementation when older UI copy describes different limits. Git LFS and Actions can have usage limits or charges; check the user's account before committing to large sync volumes.

Public repositories can serve original saved media directly. Private-repository static builds create resized image copies for the published site; videos can link to their source instead. The generated static archive currently retains the original card presentation rather than the local server's alternative interfaces. Do not promise that every local reading style is exported to Pages.

The database is attached to the posthole-index release because rewriting it in Git would grow history. It includes full-text search and vector data. The current schema describes the model and query format, but a custom semantic-search UI is separate work. Check the workflow result, Pages deployment and database artifact independently; one successful push does not prove all three completed.

Privacy, storage, and backups

An archive can reveal more than the text of public posts. It includes the posts a person encountered, capture times and page context, relationships to reply threads, downloaded media, and potentially content accessible only in their signed-in session. Raw responses and source data are especially detailed. Treat the local archive as the user's data, not an automatically shareable demo dataset.

The helper excludes certain responses that can contain sign-in material from sync, but filtering is not a reason to assume an archive is safe to publish. Review what will leave the computer. Do not upload raw responses to an issue tracker, send a whole archive to another service, or commit browser credentials as a debugging shortcut. For parser reports, prefer the smallest redacted fixture that reproduces the problem.

There is no total-size quota or retention policy in the settings shown above. Video, raw capture, repeated responses, and deep thread expansion can grow quickly. Agree on a storage budget and how the person will check usage. Disabling downloads or capture does not reclaim existing files. Plan cleanup separately, back up first, and obtain the user's choice before deleting anything.

Back up the complete archive tree, including index/, post records, media, and raw/ if kept. Back up source changes separately. Browser-local keeps and read history are not automatically part of a filesystem copy of the archive. A Git mirror is not a substitute for checking recoverability: large files may be skipped, credentials may expire, and remote deletion or history changes can propagate.

If a previously pushed archive contained material the user did not mean to share, stopping sync prevents future pushes but does not remove existing Git history, releases, Pages deployments, caches, or other copies. Treat remediation as a distinct task; do not promise that deleting a local file retracts published data.

Update, move, or repair an existing setup

Identify the loaded extension directory, helper registration path, active Node path, archive root, viewer working directory and port before changing anything. Inspect source status and back up important settings and data. Update the existing installation in place when practical, preserving local modifications and the manifest key. Build from that checkout; do not accidentally reload a different dist directory from another clone.

The popup's Check for updates asks the native helper whether a newer local build exists. It does not pull source from GitHub. For an unpacked installation, fetch the intended source update and run npm run build first. The running extension generally detects the new build itself. If detection does not occur, inspect the helper and loaded path, then reload the correct extension deliberately.

Reinstall viewer dependencies if its package/lockfile changes and restart its server after relevant source updates. Rerun helper installation after moving the program or changing Node. Do not move the archive merely because the program was updated. Test capture and viewing again after an update, not just the extension's version number.

When moving to another computer, install and register the program for that computer's browser and Node paths, copy the archive safely, select the copied root, and test it. A native-messaging manifest or generated launcher from another machine is not portable. Browser-local preferences and read/keep history need separate consideration.

Troubleshooting by symptom

The popup shows a red exclamation mark or “helper unavailable.” Verify Node is executable, the generated launcher still exists, the native manifest names com.imbue.posthole, its path matches the current program folder, allowed_origins matches the installed extension ID, and it was registered for the actual browser being used. Inspect browser policy or sandbox restrictions. Rerun registration after a path change. Do not make the allowed origin unrestricted.

The helper connects but no posts arrive. Check paused state, the source toggle, the archive path and permissions, the intended browser profile, and whether the supported page was loaded after installation. Reload a supported tab and watch the extension service-worker console for a focused error. Some content is not a supported post shape; a platform parser may require an update. Avoid collecting a whole signed-in network trace when a small redacted sample will do.

Only replies are missing. Check fetchThreads, depth, page limit, queue status, and the site's signed-in tab. Threads may need one opened post to establish a request shape. Rate limits and deleted or restricted replies can prevent completion. Check site-specific errors before increasing limits.

Images or video are missing. Check the corresponding download toggle, maximum per-file size, write permissions and extension errors. A saved record can appear before its media finishes downloading. Original CDN URLs can expire. An absent local file is not fixed by a viewer color change. Some formats or remote sources may not be playable in every browser.

The viewer is empty. Confirm it points to the actual archive root and that index entries and post records exist there. Clear source/search filters and check ordering. Verify the browser URL's port matches the running server. An empty demo page on posthole.ink is unrelated to the contents of the user's local archive.

The viewer will not start or the port is occupied. Verify Bun and viewer dependencies, inspect the terminal error, and identify the process using the port. Choose another port rather than terminating an unrelated service. If the chosen archive has restrictive permissions, correct the user's access without making the folder writable to everyone.

The viewer shows stale code after an update. Restart the correct viewer process, verify its working directory, and reload the page. Multiple checkouts and multiple listening ports can make a working update appear ineffective. Check the actual source paths before deleting browser data, because clearing site data can erase browser-local reading state.

Git sync fails. Inspect the exact repository, remote, branch, authentication, network access, Git LFS availability and skipped-file result. Confirm GitHub settings allow the workflow and Pages where needed. A remote branch changed on another machine may require reconciliation. Do not force-push, discard local work, make a repository public, or remove large files without the user's intended plan.

A source parser stopped working after a social-site change. Record the source revision, source platform, a minimal example of the failure and relevant redacted error messages. Check current source and fixtures. Add a focused parser regression test for a code fix, rebuild the extension, and verify a real capture. Keep raw signed-in responses private unless the user explicitly approves a redacted reproduction.

Rebuild records from raw captures

Rebuilding is useful after a parser improvement when raw responses were kept. It cannot invent responses that were never archived or recover all deleted content. First back up the archive, identify the code revision to use, and prefer a new output directory so the original stays available for comparison.

From the program checkout, an example that writes to a separate destination is:

npm run rebuild -- /absolute/path/to/archive /absolute/path/to/rebuilt-archive

Inspect the rebuilt records and compare representative posts, media references, index behavior and viewer rendering before switching roots. The rebuild script also supports in-place use when no output directory is supplied; do not choose that destructive-in-effect path by default. Confirm the installed script's current arguments before running it.

Help the user change Posthole

First decide whether the request is a setting change, a reading preference, a data operation, or a source-code feature. Prefer an existing setting when it provides the desired behavior. Explain when a requested feature does not exist instead of claiming that a hidden option will enable it. Keep changes narrow, preserve data, and follow applicable repository instructions.

The extension implementation lives in src/. Parsers are under src/parsers/. src/background.js coordinates capture, thread queues and media downloads. The native writer and sync code is host/posthole-host.mjs. The viewer lives in viewer/; viewer/interfaces.ts owns the style catalog, and views.tsx, interface controls and CSS own shared rendering and navigation. scripts/install-host.mjs controls native registration; scripts/package.mjs creates the downloadable distribution. github/ contains the installed workflow/indexer templates.

Inspect actual source before editing. For a bug, reproduce the failure, identify the smallest relevant module, add a meaningful regression test where appropriate, run the relevant checks, rebuild, and verify actual behavior. Do not add a demo-only imitation of a feature that should exist in the real viewer. Keep source identity, media paths, escaped text, reply lookup, keyboard navigation and browser-local state working across interfaces.

For this project's maintained website, the extension, local viewer and posthole.ink demo must stay synchronized. Follow their AGENTS.md instructions. After viewer changes, regenerate website interfaces from the real viewer, run the viewer-snapshot check, run viewer and website tests, and publish the matching protected website build. After extension changes, rebuild/test the extension and refresh the website's downloadable ZIP from the real source. Do not hand-edit the ZIP or copy private archive data into a demo.

Useful development commands from the extension checkout:

npm test
npm run test:viewer
npm run build
npm run package

Browser end-to-end tests are available through npm run test:e2e and can interact with supported sites; inspect their requirements and scope before running them. From the website checkout, npm run render:interfaces, npm run check:viewer, and npm test verify the demo snapshot. Website hosting/authentication changes are separate from local capture; preserve the existing password protection unless the user asks to change it.

Pause, uninstall, or stop using it

To stop collection temporarily, pause saving in the extension. Stop an active auto-scroll run and review the reply-fetching control if the user wants background activity reduced too. To stop the viewer, stop its process or the specific user-level service that was installed for it. Do not terminate unrelated Node/Bun processes.

To uninstall, disable/remove the extension in the intended browser profile, stop the viewer, and remove native-helper registrations from the program checkout:

node scripts/install-host.mjs --uninstall

If registration used --dir for a custom location, supply that same directory during uninstallation. Review the installer output to confirm which manifests were removed. Uninstalling the browser extension or helper does not itself delete the archive, remove cloud backups, or retract published GitHub data. Offer to keep or separately remove the program folder and archive according to the user's request; do not delete either automatically.

End with a useful handoff
